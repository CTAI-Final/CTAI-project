# 多车辆配送路线优化项目规则（中文审核稿 v0.2）

> Computational Thinking for AI · 2026年11月13日

本项目比较三种自行实现的配送优化算法。配送性能实验在统一环境和 30 秒预算下比较可行性与方案质量；规模实验在同一算法固定工作量的条件下测量计算耗时，支持理论复杂度分析。两组均要求满足相同的配送业务规则。

本文整理已确认规则，供出题方审核后向组员发布。标为“建议细则”或“待审核”的内容尚未单独确认；候选算法仅供选择，不代表已经分配。当前交付为规则文件，不包含已经实现的测试程序、场景数据或实验结果。审核通过后再生成英文版。

## 三 必须满足的配送规则

- 每个客户必须恰好服务一次，全部货物须由同一辆车一次送完，不允许拆分配送。
- 一辆车可以服务多个客户，但只能执行一轮；出发时装好所有分配货物，所装货物总重量不得超过 100 千克。
- 不允许中途回仓补货。配送结束必须回仓，回仓后不再出发。
- 车辆数量为最多可用数量，允许闲置；闲置车辆不计行驶距离或配送耗时。
- 时间窗 [a, b] 为允许开始服务的闭区间。提前到达须等待至 a；开始服务不得晚于 b。服务可以在 b 之后结束。
- 所有正式场景保证至少存在一个合法方案。算法未找到合法方案，不等于场景无解。
- 不要求保证全局最优。保留的出题方验证路线只证明有解，不自动构成最优标准答案。

## 四 优化目标与计算口径

主目标是最小化全部任务完成时间，即从统一时间 0 到最后一辆执行配送的车返回仓库的时刻。它不是各车辆耗时之和，也不是算法求解耗时。

方案更新顺序：先比较全部任务完成时间，再比较总行驶距离；两者都相同则保留先找到的方案。不设置加权综合总分。

两地点 i 与 j 之间的距离与行驶时间按下式计算：

$$d(i,j)=\sqrt{(x_i-x_j)^2+(y_i-y_j)^2}$$

$$\tau(i,j)=\frac{d(i,j)}{v},\quad v=0.5\ \text{公里/分钟}$$

沿每辆车的路线依次推算时间。设 j 为当前地点、i 为其前一地点，客户 j 的时间窗为 $[a_j, b_j]$，固定服务时长为 5 分钟，则：

$$A_j=E_i+\tau(i,j),\quad S_j=\max(A_j,a_j),\quad E_j=S_j+t_s$$

$$S_j\le b_j$$

第一段自时间 0 由仓库出发，最后一段计入回仓路程。

车辆 k 的回仓时间、全部任务完成时间与总行驶距离按下式计算：

$$C_k=E_{L_k}+\tau(L_k,0)$$

$$T=\max_k C_k$$

$$L=\sum_{(i,j)\in R} d(i,j)$$

其中 $L_k$ 为车辆 k 服务的最后一个客户，R 为全部使用车辆路线上的路段集合。

检查器同时验证输入字段、客户编号、车辆数、起终点、客户覆盖、重复服务、容量和时间窗。候选方案若违反任意一条硬约束，即不能成为合法结果。

建议细则：内部使用完整浮点精度，展示时再保留小数；数值比较容差建议为 $10^{-6}$（对应各自单位），不得逐路段四舍五入后再累计。正式容差在接口发布前冻结。

## 五 两类实验的运行与停止规则

**配送性能实验（15 个约束难度场景）**：每次求解上限 30 秒，可提前结束。运行过程中通过公共接口保存当前最好合法方案；超时采用截止前已保存的最佳合法方案，没有则记为失败。外部测试程序负责计时和停止。

**规模实验（9 个规模场景）**：不再以 30 秒作为正常停止条件。对同一种算法，在全部规模上固定工作单位、目标工作量和相关参数，完成后停止并记录实际求解耗时。这里固定的是迭代等控制量，不是底层运算次数；每步成本可以随客户数增长。

工作量示例：贪心算法完整执行一次构造；模拟退火固定候选邻域尝试次数；遗传算法固定种群大小和代数。重启、修复和初始解构造须有明确计数或重试上限，不能因难度增加无限补做。不同算法工作单位不同，相同迭代数不代表等量计算，规模曲线主要用于各算法自身的增长分析。

规模组可另设防止失控运行的保护上限，具体秒数待审核，不默认沿用 30 秒。触及保护上限或在规定工作完成前异常退出，标记为未完成，保存实际工作量和已耗时间；不得把保护上限作为完整运行时间，也不得通过降低大规模的目标工作量制造可比曲线。算法正常完成构造但未找到合法解，可作为已完成计算过程的计时样本，同时记录求解失败。

两组共用计时边界建议：输入读取及公共预处理在计时前完成；算法自身初始化、构造、搜索和运行中的方案提交开销计入；最终复核、统计、绘图不计入。公共距离矩阵等预处理成本须单独记录并在理论分析中说明。规模组应注明曲线测量的是求解阶段；若报告端到端耗时，再加上统一预处理成本。

## 六 场景与重复实验

| 实验组 | 配置 | 场景数 |
|---|---|---|
| 约束难度组 | 20 客户、4 车辆；简单、中等、困难各 5 个；每次最多 30 秒 | 15 |
| 规模组 | 10/20/40 客户配 2/4/8 车辆，各 3 个，中等约束；每算法固定工作量计时 | 9 |
| 公开练习组 | 简单、中等、困难各 2 个；与正式数据不同 | 6（不计正式统计） |

正式测试共 24 个场景，每种算法每场景运行 5 次，共 120 次/算法、三种算法合计 360 次。其中配送性能实验为 15 × 5 × 3 = 225 次，求解预算最多 6,750 秒，即 112.5 分钟；规模实验为 9 × 5 × 3 = 135 次，耗时由完成规定工作量所需时间决定。因此不能再将全部实验上限写成 180 分钟，总耗时需另加规模实验及启动、验证、输出开销。

同一场景重复运行时，客户和车辆数据完全不变，只改变算法随机种子。建议统一使用 [1,2,3,4,5]，此具体列表待审核。算法须控制其使用的随机数来源；确定性算法也运行 5 次，用于观察耗时波动。

全部正式测试在同一台电脑、同一 Python 与依赖环境中串行运行。记录环境、代码提交版本、种子和运行状态，避免并行争抢资源影响耗时。

## 七 场景难度生成与保密

负载率 ρ 定义为客户货物总重量与车队可用总载重之比：

$$\rho=\frac{\sum_{i=1}^{n} w_i}{K\cdot Q}$$

其中 $w_i$ 为客户 i 的货物重量，n 为客户数，K 为可用车辆数，Q = 100 千克为单车载重上限。通过负载率、时间窗余量及空间与时间窗冲突共同调整难度。客户数和车辆数在原有 15 个场景中保持不变。

| 因素 | 中等难度设计方向 | 高难度设计方向 |
|---|---|---|
| 负载率 | 保留一定容量余量 | 容量接近用满，分配余量较小 |
| 时间窗余量 | 围绕已知可行路线服务时刻保留较宽余量 | 围绕服务时刻保留更小余量 |
| 空间与时间冲突 | 少量远距离客户具有重叠时间窗 | 多组远距离客户具有重叠时间窗 |

此前讨论的中等 70%～80%、困难 90%～95% 负载率，以及 ±20/±5 分钟的时间窗余量，只是候选示例，尚未确认为生成参数。简单场景的具体范围同样待校准。

生成方法：先构造车辆分配和路线，设置满足容量的客户重量，计算服务时刻，再构造包含这些时刻的时间窗；保留至少一套完整可行路线。调整后重新验证，不能仅检查总容量。

采用统一基础方法试跑校准等级，记录校准依据。难度不是对所有算法的绝对排序；不根据最终三位选手的胜负事后挑选数据。多个因素同时变化时，不将表现差异归因于某一个因素。规模组保持中等约束紧张程度尽量接近，车辆数按比例同步增加。

出题方提前公开规则、规模、难度范围和 6 个练习场景。正式 24 个场景及出题方验证路线不得在截止前提交到共享仓库；待算法代码冻结后，由出题方用于统一测试。保证有解，不公开对应答案。

## 八 评价指标与统计规则

| 指标 | 定义与统计口径 |
|---|---|
| 解的可行性 | 统一检查器判定；漏送、重复、超载、时间窗违规等均非法。 |
| 全部任务完成时间 | 每场景取 5 次中合法方案的平均值，主要质量指标，越小越好。 |
| 总行驶距离 | 统计合法方案的平均值；路线展示使用对应那一次的实际距离。 |
| 算法运行时间 | 性能组：全部 5 次平均求解耗时，包括失败，超时按预算记录；规模组：完整执行规定工作量的平均耗时及波动，截断记录另列，不与性能组混算。 |
| 可行解成功率 | 合法运行次数/5。分组时报告合法运行数/该组全部运行数。 |
| 完成时间波动 | 合法方案完成时间的标准差；合法次数不足 2 次时显示“不足以评价波动”。 |

本节配送质量统计主要用于 15 个性能场景。规模组的计时统计按是否完整执行规定工作量筛选，而非按路线是否合法筛选：统计完整执行记录的平均耗时和波动，同时报告完整完成率、截断及异常数量；完成工作量但未找到合法路线的记录仍计入耗时。若部分截断，均值仅代表已完成子集，须提示其偏差，不进行无条件效率排名。

建议细则：标准差使用样本标准差，分母为 $m-1$，m 是合法运行次数；该统计细则待审核。失败不记成 0 分钟；全部失败时完成时间、距离与波动为无可行结果，JSON 使用 null 而非 NaN 或 Infinity。

每个场景保留 5 次全部记录。展示路线选取合法结果中 T 最小的一次，T 相同按 L，再按先后顺序。称为“五次运行中的最佳方案”，不得直接称为全局最优。

配送性能组按简单、中等、困难汇总；规模组按 10、20、40 个客户分别汇总，主要展示完成固定工作量的计算耗时及波动。不混合两种停止规则的耗时，不将不同规模配送完成时间混成总平均值。方案质量可作为规模组的辅助结果，必须与可行率一起报告。

建议比较细则：先报告各算法完整成功率；质量对比优先使用各算法都至少成功一次的共同场景，并明确共同场景数，各场景先求合法运行均值再等权汇总。成功次数不同仍须注明；只有单方成功的场景另列，不静默剔除。无共同成功场景时不形成直接质量排名。

不把更短的失败运行耗时解释为更高效率；不把未知最优值情况下的结果报告为“最优差距”。可报告相对其他算法的实测差异，但必须注明比较基准。

## 九 可视化要求

出题方统一生成：性能组的逐场景指标表、成功率图、配送完成时间与波动图、距离比较图；规模组的客户数量与固定工作量计算耗时曲线及耗时波动，并注明车辆数量、工作量设置、完整完成次数和截断次数。保护上限终止的记录单独标注，不作为完整耗时点拟合增长趋势。

路线图绘制仓库与客户坐标，以不同颜色区分车辆，标明客户编号与访问顺序；配套显示所用算法、场景、种子、完成时间、总距离和合法性。平均指标不对应一条真实路线，不能将平均时间标在最佳路线图上。

## 十 复杂度分析要求

每位组员须从实际代码理论推导复杂度：定义客户数 n、车辆数 k、迭代数 I、种群大小 P 等实际使用的变量，分析初始化、构造、邻域生成、可行性检查及迭代次数，合成整体表达式。提交变量定义、核心步骤执行次数、单步成本、整体复杂度和实验对照解释；不得只引用算法名称对应的复杂度。

规模实验主要观察同一种算法在固定工作量下的耗时增长，为理论分析提供实证支持，不能仅凭 10、20、40 三个规模证明某一渐近复杂度。本项目 k 与 n 同步增长，报告必须说明是在 $k=n/5$ 的配置下观察；固定 I、P 等参数，并分别解释理论中这些参数的作用。30 秒截断不意味着算法复杂度为 O(1)。性能实验说明时间预算与搜索质量的取舍，规模实验说明工作量定义与耗时趋势。

## 十一 JSON 输入输出建议规范

采用 UTF-8 JSON。以下字段结构为供审核的接口草案，业务规则已确认；代码实现前应冻结字段名、错误码和版本号。客户数量与数组长度必须一致。仓库编号固定为 0，客户编号建议为 1 至 n；货物需求为正数且不大于 100，时间窗满足 $0\le a\le b$。详见 [interface_spec.md](interface_spec.md)。

| 输入字段 | 含义 |
|---|---|
| schema_version / scenario_id | 接口版本与唯一场景编号 |
| depot | 仓库 id 与坐标 x、y |
| customer_count / vehicle_count | 客户数量及最多可用车辆数量 |
| vehicle_capacity_kg / speed_km_per_min | 统一载重上限与速度 |
| service_time_min | 统一客户服务时长 5 |
| customers | 客户数组，每项包含 id、x、y、demand_kg、time_window_min |

以下为两客户格式演示，不属于正式测试场景。采用 1 辆车，两客户需求合计 50 千克，路线 [0,1,2,0] 合法。

```json
{
  "schema_version": "1.0", "scenario_id": "example_001",
  "depot": {"id": 0, "x": 10, "y": 10},
  "customer_count": 2, "vehicle_count": 1,
  "vehicle_capacity_kg": 100, "speed_km_per_min": 0.5,
  "service_time_min": 5,
  "customers": [
    {"id": 1, "x": 13, "y": 10, "demand_kg": 20,
     "time_window_min": [0, 30]},
    {"id": 2, "x": 13, "y": 14, "demand_kg": 30,
     "time_window_min": [0, 40]}
  ]
}
```

计算核对：0→1 距离 3 公里、行驶时间 6 分钟，服务结束后为第 11 分钟；1→2 距离 4 公里、行驶时间 8 分钟，第 19 分钟到达，服务结束后为第 24 分钟；2→0 距离 5 公里、行驶时间 10 分钟；全部任务完成时间 34 分钟，总行驶距离 12 公里。

建议算法只向公共接口提交 routes，公共测试程序填充实验元数据、计时和校验结果；算法自行报告的时间不作为权威评价值。每辆使用车辆一条路线，闲置车辆建议省略，实际车辆标识与结构由接口定稿。

以下输出示例对应性能模式。规模模式还需记录 experiment_mode="fixed_work"、work_budget、work_done、work_completed、safety_limit_sec；具体工作量配置与单位应由配置文件和 README 定义，字段结构待接口定稿。

```json
{
  "schema_version": "1.0", "scenario_id": "example_001",
  "algorithm_id": "solver_a", "seed": 1, "run_index": 1,
  "experiment_mode": "time_budget", "time_limit_sec": 30,
  "termination": "completed", "feasible": true,
  "routes": [{"vehicle_id": 1, "stops": [0, 1, 2, 0]}],
  "solver_runtime_sec": 0.12,
  "makespan_min": 34.0, "total_distance_km": 12.0,
  "validation_errors": []
}
```

0.12 秒仅为格式示例，不是实测结果。termination 建议记录 completed、timeout、error，规模组额外区分 safety_timeout。feasible 表示是否有合法路线，work_completed 表示是否完成规定工作量，二者互相独立。性能组超时且有合法快照可计为成功；规模组安全超时即便有合法路线也不能计为完整计时样本。无合法路线时质量指标为 null。

## 十二 算法备选方案

以下是方法级候选，不保证任何一种在本项目中最好。所有方案都必须处理客户分配、载重、时间窗和回仓；仅调用两点最短路径算法不能解决整个任务。具体参数和实现复杂度由选择者说明。

| 候选 | 核心做法与约束处理 | 实施特点 |
|---|---|---|
| 可行插入贪心与局部搜索 | 逐次将客户插入可行位置，按完成时间增量选取；用客户迁移、交换或路线内重排改进，每次检查容量和时间窗。 | 较易实现，适合作为基线；易陷入局部最优，需处理构造失败。 |
| 多起点随机贪心 | 使用多个随机或带随机性的可行构造起点，对每个起点做局部改进，保存最好合法结果。 | 中等工作量，易按时间预算停止；重启质量和多样性影响明显。 |
| 模拟退火 | 从可行方案出发，用迁移、交换等邻域搜索；按温度概率接受部分变差方案，始终保留最好合法结果。 | 中等工作量；需设计初始解、温度与降温规则，避免过早冻结。 |
| 禁忌搜索 | 迭代选择邻域方案，用短期禁忌记录减少反复回到旧状态；设置例外规则允许改进。 | 中等至较高工作量；邻域和禁忌长度需解释。 |
| 遗传算法 | 维护多个编码方案，通过选择、交叉、变异搜索；解码、修复或可行构造处理容量与时间窗。 | 较高工作量；可行性处理是重点，不应只写通用排列交叉。 |
| 小规模精确搜索 | 枚举或分支限界探索分配与顺序，在可证明界限下剪枝。 | 可作小实例校验或额外基准；30 秒内不保证适用于正式大规模实例。 |

建议选型组合为：可行插入贪心加局部搜索、模拟退火、禁忌搜索或遗传算法。该组合仅供选择。不同方法可以共用距离计算、校验和明确披露的初始化工具，但各自核心搜索逻辑须有实质区别。

内部可探索不可行候选，但公共保存接口只接受合法方案；如果采用惩罚函数，必须说明惩罚设计，最终仍按硬约束评价。所有算法都需要可行初始方案的构造或修复策略，不能直接读取隐藏验证路线。

## 十三 GitHub 协作与提交要求

共用一个仓库，每人维护独立算法目录。公共接口、练习数据、检查器、测试入口由出题方维护；正式数据在代码冻结前独立保管。当前尚未指定或创建实际仓库。

| 建议位置 | 内容 |
|---|---|
| docs/ | 审核通过的规则、接口说明 |
| data/practice/ | 6 个公开练习 JSON |
| common/ | 数据读取、距离计算、合法性检查、结果保存接口 |
| algorithms/solver_a 等 | 三位组员各自代码与 README.md |
| runner/ | 两种模式的计时、种子、停止控制、工作量记录及结果输出 |
| evaluation/ | 统计与可视化 |
| results/ | 正式测试结果；发布范围由出题方安排 |

README 必须包含算法思路、选择理由、伪代码、理论复杂度、参数、随机种子处理、局限性、依赖和运行方式。另外分别说明 time_budget 与 fixed_work 两种模式：前者的 30 秒停止策略，后者的工作单位、目标数量、初始化和重试上限、实际完成量计数及保护停止行为。同一种算法的规模组配置在正式测试前冻结。提交代码后记录 Git 版本，禁止按隐藏场景编号硬编码路线。

建议接口改为 solve(instance, seed, run_config, submit_solution)。run_config 区分 mode="time_budget"（time_limit_sec=30）和 mode="fixed_work"（work_budget 与 safety_limit_sec）。固定工作量的具体字段随算法定义，不能继续由唯一的 30 秒参数控制全部实验；接口草案定稿后统一发布。
