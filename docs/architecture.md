# Architecture

## Layers

```
data/practice/*.json
        │
        ▼
  instance.py ── validate ──▶ dict
        │
        ▼
   problem.py ── distance matrix, customer lookup, fast path simulation
        │                    ▲
        │                    │ used by
        ▼                    │
   checker.py ──▶ Evaluation (feasible, makespan, distance, per-route report)
        │
        ▼
  submitter.py ── keeps the best feasible plan, builds the run record
        ▲
        │ submit(routes)
        │
  algorithms/*.py  ◀── budget.py (time / fixed work / safety ceiling)
        ▲
        │ solve(instance, seed, run_config, submitter)
        │
  runner/experiment.py ──▶ results/**.json ──▶ evaluation/statistics.py ──▶ tables
```

## Why it is split this way

**The checker and the algorithms read the same physics.** `Problem.evaluate_path` is the only
place where speed, service time, capacity and time windows become numbers. If an algorithm
disagrees with the checker about the cost of a route, that is a bug in one place, not a silent
mismatch between two implementations.

**Algorithms cannot cheat and cannot self-report.** They receive a submitter, not a results file.
Every plan goes through `evaluate_routes`, and an illegal plan is recorded as a rejection. The
harness, not the algorithm, decides which plan is best.

**Stopping is one object.** `Budget` answers both "is my 30 s up?" and "is my work budget up?".
That is why the same algorithm code serves both experiment groups, and why the two groups cannot
drift apart in their stopping logic.

**Statistics never see the search.** `evaluation` only reads JSON records; it can be re-run on an
old result set without re-running any algorithm.

## Module map

| Module | Responsibility |
|---|---|
| `geometry.py` | Euclidean distance, distance matrix |
| `instance.py` | Scenario loading and validation |
| `problem.py` | Preprocessed scenario plus fast path simulation (`PathStats`) |
| `checker.py` | Rule validation, objective, `Evaluation` |
| `submitter.py` | Submission channel, best-plan bookkeeping, run record |
| `budget.py` | `Stopwatch`, `WorkMeter`, `Budget`, safety ceiling |
| `datagen.py` | Deterministic scenario generator with a planted feasible solution |
| `algorithms/base.py` | `Plan`, construction heuristic, relocate / swap / 2-opt operators |
| `algorithms/*.py` | The three reference algorithms |
| `runner/experiment.py` | `RunSpec`, `run_once`, `run_batch`, result files |
| `evaluation/statistics.py` | Aggregation, Markdown and CSV output |
| `evaluation/plots.py` | Optional matplotlib figures |
| `cli.py` | `check`, `solve`, `run`, `evaluate`, `data`, `demo` |

## Design decisions

**Standard library only.** The core has no third-party dependency, so a marker or a teammate
cannot get a different number because of a different NumPy build. Matplotlib is an optional extra
used only for figures.

**Cached route statistics in the search.** `Plan` keeps one `PathStats` per route. A move
recomputes only the one or two routes it touches, which is what makes a full neighbourhood scan
cheap enough for a 30 s budget.

**One construction, three searches.** All three algorithms start from the same cheapest-insertion
plan. Differences in the results therefore come from the search strategy, not from a lucky start.
This is an explicit experimental choice, documented in `docs/algorithms/`.

**Deterministic data.** `datagen.generate` is a pure function of its seed; the manifest records
the seed of every committed file, so the practice set can be regenerated byte for byte.

**Failure is data.** A crashing algorithm, an expired safety ceiling or an infeasible-only run
produces a record with `termination` set accordingly. Nothing is retried silently, because a
silent retry would hide exactly the behaviour the experiment is meant to expose.

## Testing strategy

`tests/` covers the three places where a wrong number would invalidate the whole report:

| File | What it locks down |
|---|---|
| `test_checker.py` | Objective arithmetic (12 km / 34 min on a hand-computed scenario), every rule violation, budget semantics |
| `test_algorithms.py` | Every algorithm feasible on every practice scenario; move operators never duplicate or lose a customer; seeded runs reproducible |
| `test_runner.py` | Both stopping modes, result files, crash and infeasible-only handling |
| `test_datagen.py` | Generator determinism, validity, solvability, manifest consistency |

Run them with `make test` (43 tests, about two seconds).
